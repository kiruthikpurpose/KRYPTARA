## X.1 Verdict in five lines
1. The single-fault check is sound only relative to a closed, correct list of fault sets. It is a theorem about the list, not about the world. [I]
2. Replay catch-up cannot defend a stale device against a later break of a class valid at its head (a long-range / fork attack). It only gives completeness for honest histories. [I]
3. P5 (hash-only root) and P2(a) (single-fault safety over the hash atom) are mutually exclusive unless the locked stage holds two hash families, which is core-dual and needs the unsolved independence judgement (blueprint X-05). [I, with proof sketch X.4]
4. Tighten-only plus monotone state makes every mistake and every custody loss permanent; the liveness check as stated (some set exists among slots holding keys) is too weak. 22.6% of tables passing the thesis checks survive loss of any one slot/group [C].
5. The "adversary structure = min cut order >= 2" unification is true but near-tautological; its probabilistic fault-tree reading (HFT=1) is false under common cause.

## X.2 Counterexamples to "table passes => no single event authorises an irreversible change"

### X.2.1 Quantified: a signer in two groups (or two slots, one human)
Experiment [C]: all 7,581 monotone functions on 5 slots (Dedekind number 7,581 matches known value [I]); groups OEM={0,1}, OWNER={2}, ESCROW={3,4}; assumption atoms H1={0,2,3}, H2={1,4}. Declared faults: each slot, each group, each atom. Result:
- 1,227 non-empty monotone tables pass thesis checks (a) and (c).
- 398 of them (32.4%) are authorised by some pair of slots, i.e. one event "one person/HSM/cloud tenant controls two slots" authorises. Only 829 (67.6%) are immune to every two-slot coincidence.
So passing the check carries no information about realistic coincidences unless the pair family is declared too, and the device cannot verify custody anyway (it sees key hashes). Custody group is an unauthenticated label supplied by whoever installs the policy. Same key hash in two slots, or two keys from one HSM, defeat it. Required hardening: device rejects duplicate key hashes (cheap); everything else is process, outside the proof. [I]

### X.2.2 Correlated and hierarchical custody
- Shared HSM vendor firmware, shared cloud KMS, shared signing-ceremony script, shared RNG at key generation: these are common-mode events spanning groups. Each is a fault set only if somebody thought to declare it. The "closed world" assumption is the whole safety argument. [I]
- Hierarchical custody (escrow agent's keys wrapped by OEM HSM; owner's key held by an integrator): the declared groups are disjoint on paper, joint in the key-wrapping graph. Fix: the declared fault family must be generated from a machine-readable custody graph (ancestors of each key), not hand-written. Without it the check is vacuous. [H]
- Stateful hash signatures add a signer fault that is correlated across "independent" slots with the same scheme: backup restore / one-time-state reuse at one HSM yields forgeries at that slot; if two slots are LMS under one HSM product, one operational error hits both. [I]

### X.2.3 Compromised verifier vs compromised key
Verifier code (locked stage) is a single point shared by every slot: a bug there is "all slots faulted", F=P, and by monotonicity table[P]=1 for any live policy. No truth-table property can cover it; the redundancy argument (HFT) does not apply to systematic faults (IEC 61508 distinguishes random hardware from systematic failures; redundancy does not buy systematic capability) [I]. Blueprint D-20 (complementary encodings) and D-13/D-14 (two compilers, differential tests) address it; the thesis must say the claim is conditional on that. A related hole: the lookup `table[slotmask]` is itself on the irreversible path; a fault flipping one table bit or the mask is a single physical event. Store table plus complement and check both. [H]

### X.2.4 Per-action tables and the HALT/boot exceptions
One 256-bit table cannot express "boot image: 1 OEM; floor advance: 2 groups; HALT: any 1". You need one table per action class (K x 32 B) and an exemption list from check (a): HALT is a single-signer action by design (P4), and the blueprint's BOOT_IMAGE is 1 OEM signature (D-05, section 5.4). A compromised OEM key therefore authorises arbitrary second-stage code on every fleet device. If "irreversible" includes physical consequences (actuator commands, safety-envelope changes, D-19), the lattice definition of irreversible (floor, slots, sovereign, epoch) is too narrow. The policy proves safety of the authority lattice, not of the plant. [I]

### X.2.5 Replay across actions
Signatures must be domain-separated by action, device id (or fleet id), prior head hash and epoch. If a signature over a bundle can be counted for a floor advance, the table is meaningless. This is cheap but must be a conformance vector. [H]

### X.2.6 Physical opening and state rollback
Hash chain plus state does not prevent rollback: a device whose NV is restored to an older snapshot is at an older head and accepts the honest successor and any forgeable fork (X.3). Rollback resistance must come from the monotone medium (P5's assumption), and then only the parts of state held there. Natural fit worth noting: the policy table is tighten-only, so it can live in fuses written as complement (blowing a fuse only tightens). But the slot key hashes and the retired set need N generations of fuses: 8 slots x 32 B x G generations, e.g. G=4 is 1,024 B of OTP [E: 8x32x4], often unavailable on small parts. If the retired-slot set is only in flash, an opener of one device can un-retire; this is bounded to one device (blueprint 5.9 already says "not claimed"). I give no attack method; assess per part from published evidence. [I]

### X.2.7 Malicious-but-valid tighten-only policy
Any table passing (a)+(c) can be tightened to "all 5 slots required" (passes (a),(b),(c) [C]); that policy dies when any single custody party disappears. Liveness check (c) ("a set exists among slots holding keys") says nothing about whether those key holders still exist. Stronger check: after loss of any one declared slot or group, some authorised set remains (a Hirt-Maurer-style robustness condition [I]). That removes 78% of otherwise-passing tables in the n=5 example (277 of 1,227 survive [C]), i.e. the strong check bites hard and the thesis's weak (c) is far from sufficient. Even then: the check covers only declared losses; a company failure over 40 years is a multi-party loss. The realistic recovery is a loosening path (break-glass, escrow, sovereign), which is exactly what P1/P2 forbid; the design must say which authorised join functions as the loosening and who can invoke it. If it is "all remaining parties," it reintroduces a single-fault path. [I]

A second bricking vector: REVOKE of honest slots. Retiring is a join (irreversible), authorised by the table; an attacker with an authorised set (two colluding or compromised parties) retires the victims and is the only remaining authority. Single-fault safety does not prevent it, as it is the double-fault case; but the lattice makes the damage permanent, whereas a mutable system allows later recovery. This is the cost side of monotonicity. [I]

### X.2.8 Equivocation and the malicious ledger
The device stores only head + state and (per D-10) never reads the ledger. Two valid successors of one head are both valid for the device; whichever the ledger or gateway presents first wins. Consequences:
- A malicious or compelled ledger can show device A branch 1 and an auditor branch 2; the pure-core replay by "any party" verifies each branch separately and passes both. Audit by replay proves internal validity, not uniqueness. Uniqueness needs transparency-log consistency (witnessed checkpoints) or gossip (blueprint X-13, research). [I]
- Censorship: ledger withholds the retirement transition from a device; the device continues to trust the retired slot. Availability of the correct suffix is outside the trust boundary and unfixable by devices. [I]
- Lattice-vs-chain tension: P1 promises joins (commutative, idempotent, mergeable); P3's hash chain imposes a total order. Two concurrent legitimate joins (OEM retires slot X, owner retires slot Y) from the same head create a fork that both parties legitimately signed; a stale device can follow only one. Either transitions are chain-linked (no merge, forks need an arbiter) or they are order-free joins (no hash chain, replay protection moves to per-join nonces and the "head" becomes a set digest). Pick one. [I]

## X.3 Replay / catch-up for the downgrade problem and decade-scale algorithm support

### X.3.1 The long-range fork
Stale device D at head h_k (year 2026) with slots under class X (say LMS). In 2041 class X is broken. The honest chain retired X in 2035. Attacker, able to forge X signatures, builds a fork from h_k: transitions valid under D's policy at h_k. D has no means to prefer the honest chain: both extend its head with valid signatures; the honest transitions that retire X are exactly the ones it has not yet seen. Replay "in order" works only if the honest suffix is delivered first and the device refuses anything else; attackers control the network. This is the proof-of-stake long-range/weak-subjectivity problem in OT clothing. [I]

Defences, none free:
1. Freshness anchor held on device: a monotone check against a trusted external witness (online challenge, or a "not-after" checkpoint signed by a surviving root). A device that comes up after 20 years has no clock [atlas Part 6]. So it needs a challenge-response to a party it can authenticate: which party, whose key is not the broken class? Circular unless a surviving class exists in its policy. [I]
2. Per-epoch "sealing" by the quorum: each epoch's closing checkpoint is signed by all classes still alive; device accepts forks only if sealed. A broken class can't seal. But a device stale across the break holds no sealed checkpoint of later epochs, only the old ones. Same problem, delayed. [I]
3. Honest answer: a device's security is bounded by the weakest class valid at its head until it is brought current through a channel authenticated by a non-broken key it already trusts. State this as a theorem-like limit: "catch-up safety requires at least one slot in the head policy whose assumption is unbroken at catch-up time". With the single-fault table, such a slot exists as long as only one assumption has broken: P2 helps here (that's the real benefit) — the table at head requires 2 independent classes, so forging via X alone fails. Good: so the fork attack requires a second break or a custody compromise. This rescues the design but converts the guarantee to: stale devices are safe against ONE broken class but unsafe against two broken classes over the stale period, where the "two" can be sequential in time (X breaks 2038, Y breaks 2044, device wakes 2046). Sequential breaks are exactly what 20-year-stale devices see. Fault model over time must be cumulative, not instantaneous: a single-fault check evaluated at a point in time under-counts. [I]

### X.3.2 Algorithm support for replay
- Any verifier of the full log must contain every algorithm that ever appeared in it. Over 40 years: 5+ generations (hash-based, lattice, possibly code/isogeny-based, a post-2040 replacement). Auditors replaying a log with transitions signed by since-broken algorithms obtain no assurance from those signatures; assurance needs archival timestamps (RFC 4998-style, already in the blueprint) held by witnesses. So P3 "any party replays to verify" is true only with the added axiom "log entries were witnessed before their algorithm broke". [I]
- The device can only catch up through transitions whose algorithm its installed verifier supports. The locked stage is immutable; new classes can be added only in the second stage, which per J-23 cannot be trusted to decide authority. So transitions signed only by post-ship classes cannot be authority-bearing at the locked stage. Hence every authoritative class must exist in the locked stage at shipment. The root can't be "delegated upward" in any way that reduces the locked stage's reliance. [I]
- Size [E]: 40 transitions x 2 signatures x 7,856 B (an SLH-DSA-128s-sized signature; figure from memory, unverified) = 628,480 B; at 2 kbps = 2,514 s. Fine for gateways, bad for narrowband and for verification time per transition on M0+-class parts (unmeasured). Compaction (checkpoint transitions, "skip-join" signed by current policy) reduces it but a skip-join is a new authority statement over many steps and needs the same fork analysis. [I]

## X.4 Is "assumptions as adversary-structure parties" sound?

What is right: Hirt-Maurer general adversary structures replace threshold t with a monotone family Δ of corruptible sets; safety needs access structure A disjoint from Δ [I]. Taking assumptions as "parties" whose corruption is simultaneous across all slots depending on them is a valid way to encode worst-case correlation. The equality with "minimal cut set order >= 2" holds trivially: every minimal authorised set is not contained in any declared fault set, i.e. needs events from at least two declared basic events. [I]

Fallacies and gaps:
1. Closed-world. The theorem quantifies over Δ as declared. Soundness reduces to completeness of the basic-event list. A fault-tree HFT claim is ordinarily argued by FMEA/FTA completeness plus beta-factor for common cause; here beta is unknown and is the dominant term. [I]
2. Probabilistic reading is false. For random independent faults cut-set order 2 gives probability p1*p2 (e.g. 0.05 x 0.05 = 0.0025 over a period [E]). With common-cause beta = 0.3 the dominating term is beta*p = 0.015 [E, numbers illustrative]; six times larger. Cryptanalytic breaks of related primitives are strongly correlated (shared techniques, shared quantum capability, shared reduction structure); SHA-256 and SHAKE256 share the Merkle-Damgard-vs-sponge difference but also the same hash-based-signature security proofs (multi-target second preimage, tweakable-hash arguments) and the same implementation of the signature wrapper. X-05 admits no defensible model. [I]
3. Adversary is adaptive and strategic, not random. Cost of attacking two groups is roughly additive (bribe two insiders), not multiplicative. Cut-set order maps to attacker effort only if effort per set is independent. [I]
4. Assumptions are not static parties: break events are time-varying and cumulative (X.3.1); Hirt-Maurer is a one-shot corruption model. A dynamic structure (parties join/leave, corruptions only grow) fits better and is what the lattice actually models, but then the check must be repeated at each state, and tighten-only prevents repairing a state that became unsafe. [I]
5. Two kinds of fault conflated: forgery (adversary can sign) and loss (honest can't sign). Safety needs A disjoint from Δ_forge; liveness needs complement-of-F in A for F in Δ_loss. They have different families. A hash-atom covering all root slots is a valid forge-fault but you don't need liveness against it (honest signers still sign). Without separating the two families the unification invites both false comfort and false rejection (my first computation under a mixed family returned 0 feasible tables, a modelling artefact [C]).

### X.4.1 P5 versus P2 (formal)
Let root slots R all rely on atom H only (P5). If H is in the declared fault family, safety requires table[R-slots all valid] = 0 for every authorised set drawn only from R. Then every authorised set must contain a slot outside R, i.e. a stronger-assumption slot (lattice/EC). But P5 says those are "delegated and revocable by the root", i.e. the root alone can revoke them, which requires an authorised set contained in R. Contradiction: either (i) root can act alone (violates P2(a) for atom H) or (ii) every action needs a non-root slot (root's reliance is H AND lattice: P5 false). The only consistent reading: root is the AND/2-of-2 across two hash families (core-dual) and P5 says "hash-only" meaning two hashes. Then the conflict moves to independence of the two hashes (X.4 item 2) and to ML-DSA being kept out of the quorum count (blueprint C-06 fallback). [I; derivation above, small case consistent with code: with core-nano all slots under one atom, no table satisfies both the atom-safety and "root alone suffices"]

## X.7 Conflicts with committed blueprint decisions
- D-03 says no assumption masks on core-nano; P2 puts masks and fault checks on the device. The thesis moves assumption knowledge into the immutable stage; the blueprint intentionally kept it in host tools ("Host tools always compute kappa"). If the device validates, the device must also ship and trust a custody/assumption declaration it cannot verify (X.2.1). Keep validation in host tools and make the device enforce only structural checks (monotone, tighten-only, duplicates, remaining-set liveness). Recommended compromise. [I]
- D-10: devices never read the ledger. P3's catch-up reads signed transitions via a gateway; fine, but the ledger is then in the trust path for availability.
- D-11/J-12: scoped, expiring halt; the thesis's "one-signer HALT" must keep scope and rate limits. A stolen halt key can re-issue halts if epochs advance only on authorised transitions it can starve: halts that expire on epoch count never expire if the attacker can also stall epoch advance (denial of update during the window you need a fix). Bound halts by a monotone count of halts per key per floor, not by time or epoch alone. [H]
